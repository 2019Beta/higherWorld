# 进入存档后区块加载减速与节奏波动修复

依据任务「修复并优化区块加载缓慢」「分析区块加载速度不均」，以及 `research/4` 的 18:04:10–18:10:12 转储。此次修复在已有依赖闭包缓存、地形快照释放、光照位图队列等改动上继续处理运行态暴露的问题。

## 本轮证据

`research/4` 使用 GPU 路径，与 `research/2` 的 CPU 路径不同；不能直接沿用旧报告的 GC 严重程度。原始 JFR 有效时长 360 秒，包含 25,618 个执行样本。

从 `research/4/mc-load-20260906-join/raw/exec-samples.txt` 按既有窗口统计服务器线程栈：

| 窗口 | 服务器线程样本 | `loadedFullCubes` 全量重建 | 缓存区块 tick 检查 |
| --- | ---: | ---: | ---: |
| 18:04:12–18:04:22 | 292 | 5 | 7 |
| 18:04:40–18:05:20 | 1,054 | 120 | 134 |
| 18:06:53–18:07:41 | 1,717 | 327 | 313 |
| 18:09:40–18:10:10 | 1,279 | 267 | 232 |

最后一个窗口中，这两条互斥路径合计占服务器执行样本的约 39%。这是采样占比，不是精确耗时占比；窗口来自已有分析标签，不是包吞吐计数。结束类直方图记录 33,187 个 `LoadedCube` 和同样数量的 `LoadContext`，解释了每 tick 扫描的工作规模。

直接从原始 JFR 读取的时序数据：

| 事件 | 数量 | 平均 | P95 | 最大 |
| --- | ---: | ---: | ---: | ---: |
| `jdk.GCPhasePause` | 199 | 7.52 ms | 17.04 ms | 81.31 ms |
| `minecraft.ServerTickTime` | 350 | 20.36 ms | 27.98 ms | 124.55 ms |

GC 暂停只有一次超过 50 ms；`ServerTickTime` 是周期平均 tick 时长，不能当作每个 tick 的最大值。本轮 GC 可以放大瞬时停顿，但不支持把长期快慢交替主要归因于旧采样中的秒级 GC。

## 修复内容

1. **消除随缓存扩大而增长的重复扫描。** `CubeSimulationServices` 通过 FULL 提交、卸载和上下文替换更新有序索引；每 tick 只刷新模拟窗口和实体票据，不再扫描所有缓存并复制、排序 FULL 列表。索引仍包含已经 FULL 的缓存区块，实际刷怪资格继续检查生命周期和模拟窗口。
2. **只遍历可模拟的 FULL holder。** 调度器在生命周期变化时维护集合；完成、降级、失败、取消和重新请求都会更新集合。世界 tick 保留 required、目标状态和玩家模拟距离检查，避免为了检查一批 TERRAIN/PAYLOAD 缓存而反复查找或创建 holder。
3. **超时后持续推进。** 旧的提交欠账上限为 300 ms，每 tick 偿还 6 ms 且返回零预算，可以连续跳过 50 个 tick，按 20 TPS 约为 2.5 秒。现在欠账期间保留 0.5 ms 提交预算，并以剩余 5.5 ms 偿还欠账。发送和提交分别维护平均耗时，互不污染节流信号。这是源码确认的停顿机制；转储没有逐 tick 欠账事件，不能声称每次画面停顿都已与它逐帧对应。
4. **保存、淘汰跨 tick 续扫。** 两条维护路径各保留游标，每轮最多检查 256 个缓存对象，避免重复访问开头和尾部饥饿。保持每 tick 最多保存一个快照、每次淘汰最多 32 个，以及保存成功后才移除区块的约束。弱一致迭代器取出的旧对象会用当前缓存身份校验。
5. **限制深层卸载后的光照重排。** 深层仅重新播种被移除 cube 的邻接面；高空卸载仍保留整列的天空光更新，以照顾不连续的已加载区块。

0.5 ms 是请求预算，并非不可中断的单个阶段或 GC 暂停的硬上限。仍保留首次提交前进保障，后续工作在下一 tick 继续。

## 验证与边界

- 主源码全部通过 Java 21 编译，使用本地现有 Minecraft/Fabric 依赖。
- 在 Fabric Loader JUnit 环境中运行 **54 项测试，全部通过**，无跳过或失败；覆盖队列、依赖生命周期、提交预算、模拟索引、光照边界及地形快照保留。
- 新增回归覆盖 FULL 升降级/失败/取消/重启、有序索引卸载重载、超时欠账持续推进、发送/提交耗时隔离，以及发光 cube 卸载后邻接面的光照衰减。
- `git diff --check` 通过。
- 可在本机重跑 `research/4/run-rhythm-tests.ps1`；结果输出于 `build/loading-rhythm-check/validation.log`。它使用真实 Jupiter 生命周期和 Fabric 类加载器，无替身 Minecraft 类。原始转储未被覆盖。

Gradle 离线测试被沙箱回环连接限制阻断，沙箱外重试未获批准，因此这里报告的是独立全主源码编译与 Fabric JUnit 结果，不是 Gradle build/remapJar 成功。此次没有重新进入存档采集修复后的 JFR，也没有测得端到端加载提速百分比。

复测应重新构建并启动客户端，在同一存档、相同 GPU 设置/视距下重复进入和移动，比较初始、1–2 分钟及 5–6 分钟三个阶段。预期检查点是全量扫描栈消失、欠账期间仍能推进生命周期，以及缓存淘汰能持续访问后部区块。
